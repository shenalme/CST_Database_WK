# Manufacturing LCA Database

A PostgreSQL database (for Supabase) built from the *Manufacturing LCA Database Handover Note*, plus a one-page dashboard showing sample results.
**All data in this repository is simulated.** Do not commit real company data, passwords or Supabase keys.

## What is in this repository

| Path | Purpose |
|---|---|
| `supabase/1_schema.sql` | The tables — every table and field from section 3.4 of the handover note |
| `supabase/2_views_and_security.sql` | The design-baseline calculation (views), the expected-vs-measured function, access control |
| `supabase/3_sample_data.sql` | Simulated sample rows (generated from the CSVs) |
| `supabase/4_dashboard_access_OPTIONAL.sql` | Only if the public dashboard should read live Supabase data (see below) |
| `supabase/clear_sample_data.sql` | Empties all data tables before loading real data |
| `data/csv/` | One CSV per table, same columns as the database, numbered in load order |
| `docs/` | The dashboard (GitHub Pages): `index.html`, `config.js`, `sample-data.js` |
| `tools/` | Optional: automated checks (`npm run validate`) and regeneration (`npm run build`) |

## The plan

1. **Database first, matching the note.** Same 20 tables and field names as the note; the two tables the note names without fields (`operation_energy_comparison`, `energy_actions`) get the minimum fields described in its text.
2. **Stage 1 works now.** Organisation → project → part → scenario → bill of materials and operations. Views turn this into carbon footprint per scenario using **approved, in-date factors only**; anything without a usable factor is listed in `v_bom_missing_factors` instead of silently counting as zero.
3. **Stage 2 tables exist but stay empty** until production and meter data arrive (the sample has two batches so the comparison can be shown).
4. **No TimescaleDB.** Plain PostgreSQL is sufficient until sensor readings reach roughly 100 million rows. `sensor_readings` has a `(sensor_id, recorded_at)` key so it can be converted later.
5. **Dashboard** reads three views and shows: carbon per part by scenario, a results table, expected vs measured energy, and data-quality warnings.
6. **Next, when the Excel workbook arrives:** map its columns to these tables, adjust the SQL, load the real data, and check one scenario by hand.

### Calculation rules (as built)
- Gross material = `net_quantity / (1 − waste_percentage/100)`; impact = gross × factor (factor `basis_unit` must equal the BOM `unit`).
- Electricity = `expected_energy_kwh / batch_size × lca_scenarios.electricity_factor` (carbon only).
- Process impact = process factor × (minutes per part | `process_mass_basis` kg | 1), depending on the factor's `basis_unit`.
- Scenario total = materials + processes + electricity + end of life, per finished part.

### Where this differs from the note (all minor)
- `BIGSERIAL` → `bigint generated by default as identity`, so CSV files can carry explicit ids. `TIMESTAMP` → `timestamptz` (avoids time-zone confusion).
- The note names the stage key `stage_id` in `bom_items` but `lifecycle_stage_id` in `scenario_operations`; both are kept as written and both point to `lifecycle_stages.stage_id`.
- Added rules the note asked to be agreed: part number unique within a project, codes unique, percentages 0–<100, utilisation 0–1, quantities not negative, item type from a fixed list.
- Row-level security is on for every table (otherwise Supabase would expose the tables to the internet).
- Open questions still to confirm with the team: waste convention (percent of gross input assumed), whether `expected_energy_kwh` in the workbook equals minutes ÷ 60 × kW × utilisation, and whether grid electricity should also carry energy-demand factors.

## Connect Supabase (step by step)

**A. Create the database**
1. Go to supabase.com, sign in, **New project**. Choose a name, a region your data policy allows, and a strong database password (save it in a password manager — you will not see it again).
2. Wait for the project to finish setting up (about a minute).
3. Left menu → **SQL Editor** → **New query**. Open `supabase/1_schema.sql` from this repository, copy everything, paste, press **Run**. Expect "Success".
4. New query → paste `supabase/2_views_and_security.sql` → **Run**.
5. New query → paste `supabase/3_sample_data.sql` → **Run**.
6. Check: new query → `select * from v_scenario_totals;` → you should see 4 rows. **Table Editor** now lists all tables.

**B. Make the dashboard show live Supabase data (optional)**
1. In Supabase: **Project Settings → API**. Copy the **Project URL** and the **anon public** key. Never use the `service_role` key here.
2. In `docs/config.js` paste them between the quotes and commit the change.
3. In the SQL Editor run `supabase/4_dashboard_access_OPTIONAL.sql`. This lets the public page read three result views — nothing else.
4. Reload the dashboard: the banner changes from "Simulated sample data" to "Live data from Supabase".
5. **Before loading real company data:** run the `REVOKE` line at the bottom of that file, and remove the URL and key from `config.js` (or keep the dashboard on sample data). A public page with a public key can be read by anyone.

**C. Real data**
1. Run `supabase/clear_sample_data.sql`.
2. **Table Editor → pick a table → Insert → Import data from CSV**, in the order of the numbered files in `data/csv/` (parents before children). Afterwards run `select reset_identity_sequences();`.
3. Team logins: **Authentication → Users → Add user**. Any signed-in user can read and write; nobody else can.

**D. Connect other tools (Python, Power BI, etc.)**
Click **Connect** at the top of the Supabase dashboard and copy the PostgreSQL connection string (use the pooled one for scripts). Keep it in an environment variable or `.env` file — the `.gitignore` here already excludes `.env`.

Notes: the Free plan has size limits and can pause an idle project — use a paid plan for anything the team depends on. Supabase's Security Advisor may flag the views as "security definer"; that is intentional — the views are the only thing the public dashboard can see.

## Publish the dashboard on GitHub Pages
1. Create a new GitHub repository, then **Add file → Upload files** and drag in everything from this folder (keep the folder structure; do not upload `node_modules`).
2. Repository **Settings → Pages → Build and deployment → Source: Deploy from a branch → Branch: `main`, folder: `/docs` → Save**.
3. After a minute the dashboard is at `https://<your-user>.github.io/<repository>/`. Pages sites are public.

## Changing things (optional)
Edit the SQL or the CSVs, then in `tools/`: `npm install`, `npm run build` (regenerates `3_sample_data.sql`, `docs/sample-data.js` and the two calculated CSVs) and `npm run validate` (must end "0 failed").
